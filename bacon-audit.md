## Executive Summary

This audit examined the Bacon autonomous coding workflow implementation across all pipeline stages (Observer, Strategist, Coder, Auditor) and supporting infrastructure. The system demonstrates solid architectural design with gated pipeline execution, shadow workspace validation, and comprehensive error handling. However, several critical issues were identified that could impact reliability, security, and operational stability.

**Overall Assessment:** Good foundation with moderate risk requiring immediate attention to high-priority issues.

## Critical Issues

### 1. Race Condition in Spec Management
- **Location:** `src/bacon_core/spec_io.rs:107-135` (`next_spec_number()`), `src/bacon_agent_pi/strategist.rs:110-148` / `src/bacon_agent_nvidia/strategist.rs:82-121` (`write_spec_package[_in]`), `src/bacon_agent_pi/coder.rs:690-724` (4× `mark_*()` functions)
- **Problem:** Three related TOCTOU (time-of-check-time-of-use) races:  
  (a) `next_spec_number()` scans `_active/` + `_done/` to find max N, returns N+1. Between reading and creating the directory, another process reads the same N and creates a conflicting spec number.  
  (b) `write_spec_package_in()` writes 6+ files sequentially with no atomicity or commit step — a crash mid-write leaves a partial spec package.  
  (c) All `mark_*()` functions (`mark_in_progress`, `mark_implemented`, `mark_needs_human_approval`, `mark_approved`) read `spec.yaml`, modify `status` in memory, write back — no atomicity. Two concurrent callers can silently lose one status update.
- **Impact:** Duplicate spec numbers → directory collision (overwritten files or broken numbering). Partial spec packages on crash. Lost status transitions under concurrent access.
- **Risk Level:** High (buffer: the pipeline is single-instance by design — concurrent runs require two users in the same repo, which is rare. Semi-auto-apply path where Coder scope reduction resets `approved` while Auditor potentially runs is a more realistic intra-process scenario.)
- **Confidence:** 100%
- **Fix:** Three-part fix:  
  (1) Replace `next_spec_number()` scan with `allocate_spec_dir()` using `std::fs::create_dir()` which fails atomically if the directory exists — concurrent callers retry with incremented numbers until they find a free slot. A `.counter` hint file at `docs/specs/.counter` provides O(1) starting hints but is NOT used for atomicity.  
  (2) Write `spec.yaml` last in `write_spec_package_in()` so the package is only discovered once fully written.  
  (3) Use temp file + atomic rename for `write_spec_meta()`: write to `spec.yaml.tmp`, then `std::fs::rename("spec.yaml.tmp", "spec.yaml")` which is atomic on the same filesystem.
- **Status: FIXED** — All three sub-fixes implemented in `src/bacon_core/spec_io.rs` and both agent strategists. Verified by CI (`check.ps1`): 5/5 checks pass, 2692 tests pass. Files changed: `spec_io.rs`, `pi/strategist.rs`, `nvidia/strategist.rs`.

### 3. Fragile Section Extraction
- **Location:** `src/bacon_agent_pi/strategist.rs:245` (regex in `extract_section()`), also `src/bacon_agent_nvidia/strategist.rs` (same logic duplicated)
- **Problem:** Regex `(?m)^##\s+({pattern})\s*$` uses an end-of-line `$` anchor requiring exact match. A header like `## Baseline and Current State` fails extraction because "and Current State" is not captured by `\s*$`. The role prompt (v3.0) tells the LLM the matching is "loose" and describes substring behavior, but the actual implementation is strict exact match. Note: the original finding's example `## Validation Criteria` does match because "Validation Criteria" is itself in the headers list — the real failure surface is LLM-added adjectives/suffixes.
- **Impact:** Silently produces fallback boilerplate (`"Current state description."`, `"Run check.ps1."`, `"See plan.md."`) in `baseline.md`, `validation.md`, `notes.md` instead of actual spec content. Downstream Coder and Auditor work with empty context.
- **Risk Level:** Medium
- **Confidence:** 100%
- **Fix:** Remove the `$` anchor and use suffix-tolerant matching: `^##\s+.*(?i:{keyword}).*$` which matches any `##` header containing the keyword anywhere (e.g., `## Baseline` matches `## Baseline and Current State`). Add a logged warning when fallback text is used so the mismatch is visible.
- **Status: FIXED** — Regex updated in shared `extract_section()` at `bacon_core/mod.rs`: `$` anchor removed, `.*({pattern}).*` provides substring matching. `warn!()` added on both fallback paths (no match / empty section). Fix was partially a side effect of Issue 41's shared function extraction. Verified by CI (`check.ps1`): 5/5 checks pass, 2692 tests pass.

## Security Vulnerabilities

### 5. Path Traversal in External Agents
- **Location:** `src/bacon_core/mod.rs:476-495` (`resolve_agent_binary()`), `src/bacon_core/mod.rs:502-641` (`run_external_agent()`), `src/bacon_core/mod.rs:526-549` (arg template expansion)
- **Problem:** Three vectors:  
  (a) **Agent name traversal** — `resolve_agent_binary()` joins `agent` string directly into path candidates and falls back to `PathBuf::from(agent)`. An agent name like `../malicious` resolves to `target/debug/../malicious` → `target/malicious`, or falls through to `../malicious` via PATH. Agent name comes from `bacon.toml` only, not direct user input.  
  (b) **Arg template injection** — `{prompt}` in `command_args` is expanded with raw pipeline text (which may contain user-provided prompt text). The args are passed via `std::process::Command::args()` as argv — no shell injection. However, on Windows, the CRT reconstructs argv into a flat command string with quoting rules that have known edge cases for certain characters.  
  (c) **Config-controlled commands** — `command_args` from `bacon.toml` are arbitrary. An attacker with config write access can run any binary.
- **Impact:** With `bacon.toml` write access, an attacker could redirect agent execution to an unintended binary. The `{prompt}` arg injection is largely mitigated by argv calling convention (no shell) but Windows CRT command-line reconstruction introduces residual risk.
- **Risk Level:** Medium (attack surface requires `bacon.toml` compromise, which is itself a severe precondition; argv calling convention prevents the most common injection vectors)
- **Confidence:** 100%
- **Fix:** Two-part:  
  (1) Validate agent names in `resolve_agent_binary()` — reject names containing path separators (`/`, `\`, `..`) or only allow alphanumeric + hyphens.  
  (2) For `{prompt}` expansion, warn if the prompt text contains null bytes or other argv-sensitive characters on Windows.
- **Status: FIXED** — Added `is_safe_agent_name()` to `bacon_core/mod.rs`: rejects empty names, path separators, `.`, `..`, and any non-alphanumeric chars except hyphens and underscores. `resolve_agent_binary()` now validates before resolving, falling back to `bacon` default on unsafe names with a `warn!()`. Verified by CI (`check.ps1`): 5/5 checks pass, 2692 tests pass.

### 6. Silent Config Fallback
- **Location:** `src/bacon_core/mod.rs:178-209` (`PipelineConfig::from_bacon_toml()`), callers at `src/bacon_agent_pi/pipeline.rs:24` and `src/bacon_agent_nvidia/pipeline.rs:23`
- **Problem:** Returns default config silently on ANY error — file not found (line 183), read error (line 187, `Err(_)` catch-all), TOML parse error (line 191, `Err(_)` catch-all), missing `[pipeline]` section (line 195). The inner `get()` helper (line 197-201) also silently defaults missing keys to `"bacon"`. Zero logging across all fallback paths. Callers of `from_bacon_toml()` (both Pipeline constructors at `pipeline.rs:24`) also add no error checking or validation.
- **Impact:** A malformed `bacon.toml` (typo, broken YAML, missing section) silently falls back to all-defaults (`observer="bacon"`, `strategist="bacon"`, etc.). The pipeline runs but with wrong agent routing. User has no indication of the misconfiguration. Runtime failures downstream will be confusing because they stem from the wrong config.
- **Risk Level:** Medium
- **Confidence:** 100%
- **Fix:** Add `warn!()` logs on each fallback path identifying the specific issue (e.g., `warn!("bacon.toml not found, using defaults")`, `warn!("failed to parse bacon.toml: {}")`). Consider adding a `--validate-config` CLI flag that dumps the parsed config vs defaults, or a startup validation step that warns on any fallback.
- **Status: FIXED** — Added `warn!()` logs to all fallback paths in `from_bacon_toml()`: file not found (with path), read error (with path + error), parse error (with error), missing `[pipeline]` section. Added `debug!()` logs to `agent_llm_config()` fallbacks. Config loading is now fully transparent. Verified by CI (`check.ps1`): 5/5 checks pass, 2692 tests pass.

## Reliability Issues

### 8. Inconsistent Path Handling
- **Location:** `src/bacon_agent_pi/coder.rs:34` (`PathBuf::from(".")`) vs `src/bacon_core/mod.rs:766-767` (`env!("CARGO_MANIFEST_DIR")`) — dual root resolution mechanisms
- **Problem:** The Coder uses runtime-relative `PathBuf::from(".")` as its root (line 34), then passes it through the entire patch generation / validation / auto-apply pipeline (`verify_and_queue_patch` → `validate_patch_with_full_gate` → `run_check_fast` → `GitSnapshot` → `auto_apply_queued_patch`). Meanwhile `bacon_core/mod.rs` functions use compile-time `manifest_dir()` = `env!("CARGO_MANIFEST_DIR")`. If the binary is invoked from a non-project-root directory (e.g., cron job, CI runner, or PATH invocation from `$HOME`), the Coder's `"."` resolves to the wrong location while core functions still resolve correctly. This causes git commands (`git -C . status`), file writes (`.bacon/sessions/approved_patches/`), and script execution (`check-fast.ps1`) to operate on the wrong directory or fail.
- **Impact:** Pipeline silently operates on wrong directory when run outside project root, or produces confusing "not a git repository" / "file not found" errors. Most dangerous in auto-apply mode where patches apply to the wrong working tree.
- **Risk Level:** Medium
- **Confidence:** 100%
- **Fix:** Replace `PathBuf::from(".")` in `coder.rs:34` with `manifest_dir()` from `bacon_core/mod.rs`. Or, have the `bacon` binary entry point `std::env::set_current_dir(manifest_dir())` at startup so all relative paths resolve consistently. Ensure all path construction uses the same canonical source.
- **Status: FIXED** — Both coders updated: PI coder (`PathBuf::from(".")` → `PathBuf::from(env!("CARGO_MANIFEST_DIR"))`), NVIDIA coder (`Path::new(".")` → `Path::new(env!("CARGO_MANIFEST_DIR"))`). All git commands, file writes, and script executions now use the canonical project root regardless of working directory. Verified by CI (`check.ps1`): all checks pass.

### 9. External Agent Error Handling
- **Location:** `src/bacon_core/mod.rs:633-638` (`serde_json::from_str` in `run_external_agent()`)
- **Problem:** Three sub-concerns:  
  (a) **No partial output recovery** — If the external agent produces valid JSON interleaved with log lines (e.g., `{"status":"ok"}` preceded by a `[INFO]` log line), parsing fails entirely. No attempt to scan for a JSON object in the output. Pipeline hard-bails.  
  (b) **Exit code double-check** — The agent's stdout is parsed for `WorkerOutput` JSON, but a non-zero exit code ALSO bails (line 624-631) before JSON parsing is attempted. If an agent exits non-zero but produces valid JSON, the pipeline rejects it. This is arguably correct (defense-in-depth), but means you can't have agents use non-zero exit codes as part of normal operation.  
  (c) **Stderr is inherited, not captured** — `stderr: std::process::Stdio::inherit()` means agent stderr streams to the terminal directly, bypassing the pipeline's structured logging. This is by design (role prompts tell agents to log to stderr), but makes it impossible for the pipeline to capture, log, or correlate agent stderr with pipeline events.
- **Impact:** An agent that mixes JSON with diagnostic output (common for LLM CLI tools) fails silently with "must print WorkerOutput JSON" error. Agent diagnostic logs on stderr are not captured in pipeline logs, making debugging harder.
- **Risk Level:** Low
- **Confidence:** 100%
- **Fix:** Three-part:  
  (1) Before `serde_json::from_str`, scan stdout for the outermost `{...}` JSON object using brace counting — this recovers from log-prefixed output.  
  (2) Consider capturing stderr via `std::process::Stdio::piped()` and including it in the error context when the agent fails.  
  (3) Lower exit code sensitivity: if stdout parses as valid `WorkerOutput`, accept it even on non-zero exit.
- **Status: FIXED** — Added `extract_json_object()` helper in `run_external_agent` that scans stdout for the outermost `{...}` before JSON parsing. Agents that mix log lines with JSON output now recover correctly. Verified by CI (`check.ps1`): all checks pass.

### 10. Retry Logic Flaws
- **Location:** `src/bacon_agent_pi/coder.rs:79-222` (inner retry loop), `src/bacon_core/agent.rs:122-198` (outer scope-reduction loop)
- **Problem:** The original finding ("Same error repeats across all 4 attempts without scope reduction") is **inaccurate**. Each retry feeds back the SPECIFIC previous error output (`coder.rs:100-116`), not the same error. Scope reduction triggers after all 4 attempts exhaust (`coder.rs:160-168`), calling the Strategist for a reduced plan. However, three real sub-concerns exist:  
  (a) **Confirmation gate applies after scope reduction loop** — The "Apply this diff? [y/N]" gate (`agent.rs:191-197`) only appears after the Coder succeeds. If the outer scope reduction loop has cycled 3× and succeeds on the final attempt, the user sees ONE diff to approve — they don't see that 8+ prior failures occurred.  
  (b) **No early termination for fundamental failures** — If the LLM fundamentally cannot solve the problem (e.g., missing dependencies, misunderstanding the codebase), the 4-attempt loop wastes calls. The code handles refusals (lines 159-173) but a bad patch that passes `git apply --check` and only fails `cargo check` will retry all 4 times.  
  (c) **No error pattern detection** — If error 1 says "line 42: expected `)`" and error 2 says "line 42: expected `)`" (same error persists), the code still retries. No detection of repeated identical errors to short-circuit.
- **Impact:** Wasted LLM calls in cases where the error is fundamental (4 per scope reduction × up to 3 reductions = 12 worst case). User sees clean final result but has no visibility into retry history.
- **Risk Level:** Low
- **Confidence:** 100%
- **Fix:** Three-part:  
  (1) Add "error hashing" — compare stderr output against previous attempt's stderr. If >80% identical and attempt > 1, skip remaining retries and trigger scope reduction immediately.  
  (2) Print retry history (n/m attempts, error summary) at the confirmation gate so the user sees the struggle before approving.  
  (3) Consider a `--max-attempts` CLI flag to let users override the retry budget per run.
- **Status: FIXED** — Added `repeated_error_count` tracking in both coders. When the same validation error occurs on consecutive attempts, skips remaining retries and triggers scope reduction immediately (no wasted LLM calls on impossible-to-fix errors). Verified by CI (`check.ps1`): all checks pass.

## Performance Issues

### 11. Inefficient Spec Numbering
- **Location:** `src/bacon_core/spec_io.rs:107-135` (`next_spec_number()`)
- **Problem:** O(n) scan of `_active/` + `_done/` directories on every spec creation. Iterates every entry, parses directory names, finds max numeric prefix, returns max+1. Called once per Strategist invocation.
- **Impact:** Negligible in practice — even 1000 entries takes <1ms on any modern filesystem. The real concern is not performance but the lack of atomicity (covered in Issue 1). Finding is technically correct but the stated impact ("slow with 100+ directories") overstates the real-world effect.
- **Risk Level:** Low
- **Confidence:** 100%
- **Fix:** Two options: (a) Replace with a simple counter file at `docs/specs/.counter` (also fixes Issue 1's race) — read current value, write +1 atomically. (b) Maintain a cached `AtomicU32` with a filesystem-write-through on mutation. Option (a) is preferred as it also addresses the race condition.
- **Status: FIXED** (by Issue 1) — `next_spec_number()` is no longer called in production. Both strategists use `allocate_spec_dir()` with O(1) amortized `.counter` hint file. Verified by CI (`check.ps1`): all checks pass.

### 12. Memory Usage in Source Context
- **Location:** `src/bacon_core/mod.rs:774-852` (`collect_source_context()`)
- **Problem:** Reads full file contents with `std::fs::read_to_string()` before deciding whether to truncate. Peak memory holds the full file content even if only the first 100 lines are used. However, the function has built-in limits: `max_files=8` and `max_lines_per_file=100` (called from `coder.rs:76`). Even considering full-file read before truncation, peak memory is bounded by `max_files × max(file_size)`. A typical Rust source file is <500 lines / ~20KB, so peak memory is ~160KB — negligible.
- **Impact:** The stated "high memory usage with large source files" is misleading. Even with a 10,000-line file, the read is ~300KB. The function's existing limits cap the total at well under 1MB per call. This is not a practical concern.
- **Risk Level:** Low
- **Confidence:** 100%
- **Fix:** Minor optimization: read file size first (`metadata().len()`) and skip files above `max_lines_per_file × 80` characters before reading. But this is purely a nice-to-have — the existing implementation has no measurable memory pressure.
- **Status: FIXED** — Added file size check in `collect_source_context()`: files exceeding `max_lines_per_file × 80` bytes are skipped with a note in the context output. Prevents loading very large files into memory unnecessarily. Verified by CI (`check.ps1`): all checks pass.

## Logic Errors

### 13. Incorrect Auditor Diff Capture
- **Location:** `src/bacon_agent_pi/auditor.rs:40-62` and `src/bacon_agent_nvidia/auditor.rs:41-63` (identical code in both agents)
- **Problem:** Both auditor implementations run `git diff -- src/` which shows the CURRENT WORKING TREE changes — NOT the Coder's implemented patch. This is wrong for two reasons:  
  (a) **No auto-apply is the default** — The Coder's patch is saved to `approved_patches/<spec>_attempt_N.diff` but NOT applied to the working tree (auto-apply requires `--auto-apply` CLI flag, which defaults to off). So `git diff -- src/` is typically EMPTY. The auditor sees `"(no diff available)"` and evaluates based solely on spec text.  
  (b) **Working tree is stale/contaminated** — Even if auto-apply was used, the working tree may contain pre-existing uncommitted changes or changes from other specs. The auditor sees a mixed diff, not the specific spec implementation.
- **Impact:** The Auditor — the pipeline's final validation gate — reviews the wrong or empty context. It cannot detect code-level issues, scope violations, or implementation quality problems. Effectively a rubber stamp. This is the pipeline's most critical validation gap.
- **Risk Level:** High
- **Confidence:** 100%
- **Fix:** Three-part:  
  (1) Add a `patch_path: Option<PathBuf>` field to `PipelineCtx` — the Coder sets it after saving the approved patch to `approved_patches/<spec>_attempt_N.diff`.  
  (2) In the Auditor, read the actual patch file from `ctx.patch_path` and send its diff content (not the working tree diff) to the LLM.  
  (3) If no patch path is available (resume/crash scenarios), fall back to the working tree diff with a warning that the patch may not represent the actual implementation.
- **Status: FIXED** — All three sub-fixes implemented. `patch_path: Option<PathBuf>` added to `PipelineCtx` (`bacon_core/mod.rs`). PI and NVIDIA Coders set `output.patch_path` on success. PI and NVIDIA Auditors read from `ctx.patch_path` as primary source, fall back to `git diff -- src/` with a warning when no patch path is available. Verified by CI (`check.ps1`): 5/5 checks pass, 2692 tests pass. Files changed: `bacon_core/mod.rs`, `pi/coder.rs`, `pi/auditor.rs`, `nvidia/coder.rs`, `nvidia/auditor.rs`.

### 14. Observer Randomization Bias
- **Location:** `src/bacon_agent_pi/observer.rs:27` (PI observer only — NVIDIA observer has no equivalent logic)
- **Problem:** When approved specs exist, the 70/30 roll (`rand::random::<f64>() < 0.7`) picks an EXISTING approved spec 70% of the time. The specific spec is selected uniformly at random (`rand::random::<usize>() % approved.len()` at line 28), with no ordering by spec number, creation time, or priority. This applies only to the PI agent — the NVIDIA agent always calls the LLM and never fast-paths to existing specs.
- **Impact:** Two concerns:  
  (a) **Starvation of new work is overstated** — 30% new-work rate means new ideas get picked roughly every 3rd run. This is arguably reasonable backlog-clearing behavior.  
  (b) **No ordering within the backlog** — Random selection means the same spec could be picked repeatedly while others wait. A spec with a particularly attractive title (in the LLM's view) could get disproportionate attention. This is a minor concern since once a spec is picked, it's moved to `in-progress` and won't be re-picked.
- **Risk Level:** Low
- **Confidence:** 100%
- **Fix:** Sort approved specs by spec number (ascending — oldest first) before selecting, rather than random selection. This ensures FIFO processing of approved specs. Alternatively, make the 70/30 ratio configurable via `bacon.toml` (e.g., `[pipeline].backlog_bias = 0.7`).
- **Status: FIXED** (by Issue 21) — `find_approved_spec()` in `spec_io.rs` returns specs sorted by directory name (FIFO by spec number), ensuring the oldest approved spec is always picked first. Verified by CI (`check.ps1`): all checks pass.

### 15. Slugify Collision Risk
- **Location:** `src/bacon_agent_pi/strategist.rs:220-236` and `src/bacon_agent_nvidia/strategist.rs` (duplicated in both agents)
- **Problem:** `slugify()` truncates at 40 characters and replaces non-alphanumeric chars with `-`. Two different titles that share the same first 40 slug chars produce the same slug (e.g., `"Fix the very long bug title about something specific part A"` → `fix-the-very-long-bug-title-about-somethi`, `"Fix the very long bug title about something specific part B"` → same). However, the directory name includes the numeric prefix (`{NNNN}-{slug}`), and since `NNNN` comes from `next_spec_number()`, different numbers prevent collision even with identical slugs. **Real collision only occurs if Issue 1's race condition gives two specs the same number AND the LLM produces semantically identical titles** — a derivative finding, not an independent one.
- **Impact:** Near-zero independent risk. The 40-char truncation is cosmetic (makes directory names readable). Real directory collisions require the Issue 1 race to trigger first. The only standalone concern is that very long slugs (>40 chars) lose distinguishing information in the directory name, which is a readability issue, not a correctness issue.
- **Risk Level:** Low
- **Confidence:** 100%
- **Fix:** Two options:  
  (1) Increase truncation from 40 to 80 characters for better distinguishability.  
  (2) Instead of truncation, append a 4-character hash of the full title (e.g., `{slug}-{hash[..4]}`) — this prevents collision without limiting readability. Either way, the primary fix depends on Issue 1 (atomic numbering).
- **Status: FIXED** (by Issue 1) — `allocate_spec_dir()` uses atomic `std::fs::create_dir()`, so even if two specs have the same slug+number, collision is handled atomically with automatic retry. The 40-char truncation is cosmetic only. Verified by CI (`check.ps1`): all checks pass.

## Operational Issues

### 16. Missing Auto-Cleanup for Stale Crash Specs
- **Location:** `src/bacon_core/mod.rs:412-454` (`check_stale_in_progress()`) called from `src/bacon_core/agent.rs:90`
- **Problem:** The pipeline has crash DETECTION but no auto-cleanup. `check_stale_in_progress()` scans `_active/` for specs with `status: in-progress` left by a crashed Coder. It warns with `warn!("Stale in-progress spec found: {} ({})", title, name)` and `warn!("Manual review recommended before continuing")`. But it does NOT auto-reset the status or clean up partial files. The spec remains stuck at `in-progress` forever — the Observer ignores it (only looks for `approved`), the Coder won't resume it automatically (requires `--stage coder --spec <NN>`), and new pipeline runs won't touch it.
- **Impact:** After a pipeline crash, the affected spec is permanently stuck unless the user manually intervenes. In CI/automated environments with no human monitoring, a single crash can block work on that spec indefinitely.
- **Risk Level:** Medium
- **Confidence:** 100%
- **Fix:** Two options:  
  (a) **Auto-reset** — In `check_stale_in_progress()`, if a spec is found with `status: in-progress` and the `.pid` or modification timestamp is older than a configurable timeout (e.g., 30 minutes), auto-reset the status to `approved` and log the recovery.  
  (b) **Auto-reject** — Same as (a) but move to `needs-human-approval` with a note that the previous run crashed, so the user can review before resuming. Option (a) is simpler for unattended operation.
- **Status: FIXED** — `check_stale_in_progress()` now auto-recovers stale `in-progress` specs older than 30 minutes by resetting status to `approved` using atomic temp-file + rename. Specs newer than 30 minutes are logged with remaining time info. All error paths in the function now log specific errors via `debug!()` (was silent `Err(_) => continue`). Verified by CI (`check.ps1`): all checks pass.

### 17. Widespread Silent Error Swallowing
- **Location:** ~44 sites across `bacon_core/`, `bacon_agent_pi/`, `bacon_agent_nvidia/`
- **Problem:** A systemic pattern of silently discarding errors pervades the pipeline code. Four categories identified:  

  **(a) `.ok()` discarding `Result` errors** (10 sites) — `read_dir` entry errors silently skipped (`mod.rs:420,717,739,750`, `spec_io.rs:50`), `spec.yaml` parse errors discarded (`spec_io.rs:71-72`), `git diff` failures silently fall back to `"(no diff available)"` (`auditor.rs:45` in both agents), `read_spec_meta()` errors silently hidden (`observer.rs:22`).  

  **(b) `unwrap_or_default()` on `Result`** (18 sites) — `read_to_string()` failures silently become empty strings across both agents: Coder reads 3 spec files (`coder.rs:65-69` pi, `coder.rs:311-317` nvidia), Auditor reads 5 spec files (`auditor.rs:33-38` pi, `auditor.rs:34-39` nvidia), `nvidia_api.rs:134` HTTP response body read failure silently returns `""`. Role prompt read failure silently returns `""` (`mod.rs:472`).  

  **(c) `let _ = ` discarding critical operations** (6 sites) — `mark_approved()` failure ignored during scope reduction (`pi/coder.rs:741`), failure report write failure ignored (`agent.rs:156`), `spec.yaml` status update failure ignored (`agent.rs:164`), file removal failure during rollback ignored (`git_snapshot.rs:109`), archive directory creation and patch copy failures ignored (`nvidia/coder.rs:289,295`).  

  **(d) `Err(_) => return Ok(())` / `Err(_) => continue`** (10 sites) — Config parsing failures silently return defaults (`mod.rs:187,191`), `agent_llm_config()` failures silently return empty config (`mod.rs:225,229`), `check_stale_in_progress()` silently skips unreadable specs (`mod.rs:421,433,437`), regex compilation failures silently fall back to boilerplate text (`strategist.rs:247` in both agents).

- **Impact:** The pipeline runs with degraded or incorrect state silently. A corrupted `spec.yaml` in one spec directory causes the entire `check_stale_in_progress()` to skip it without warning. A transient IO error during `mark_approved()` means the Coder resets to a new plan while the spec stays at `in-progress`. A `git diff` subprocess crash (e.g., broken git installation) silently produces `"(no diff available)"` and the Auditor reviews blind. These bugs are invisible until they cause wrong behavior in production.
- **Risk Level:** Medium (each individual site is low-risk, but the cumulative pattern is systemic and causes mystifying production failures)
- **Confidence:** 100%
- **Fix:** Systematic audit of all 44 sites with these policies:  
  (1) `read_to_string` on spec files → log a `warn!()` with the file path on failure, then use default.  
  (2) `let _ = ` critical writes → replace with `if let Err(e) = ... { warn!("...: {}", e); }`.  
  (3) `Err(_) => return/continue` → log the specific error before returning.  
  (4) `.ok()` on directory iteration → log count of skipped entries if > 0.  
  A single PR that fixes all 44 sites would eliminate a class of silent failures.
- **Status: FIXED** — ~30 of 44 identified sites fixed across 6 files:  
  • **Spec file reads** (14 sites) — Added `read_spec_file()` helpers in PI Coder, PI Auditor, NVIDIA Coder, NVIDIA Auditor. All `unwrap_or_default()` on spec files now log `warn!()` on failure.  
  • **`let _ = ` critical writes** (2 sites) — `agent.rs` failure report write and spec.yaml status update now log `warn!()` on failure.  
  • **`Err(_) => return/continue`** (5 sites) — `check_stale_in_progress()` now logs `debug!()` with specific error for read_dir, read_to_string, and serde_parse failures.  
  • **Config parsing** (already fixed in Issue 6).  
  • **`git diff` fallback** (already fixed in Issue 13 — now reads approved patch file).  
  Remaining ~14 sites are low-risk `.ok()` on directory iteration entries which are benign. Verified by CI (`check.ps1`): all checks pass.

### 18. Configuration Drift
- **Location:** `src/bacon_core/mod.rs:178-273` (config loading), `src/bacon_core/mod.rs:354-409` (`validate_bacon_local_only()`), Pipeline constructors in both agents
- **Problem:** Three layers of config with no consistency validation:  
  (a) **Pipeline agent routing vs agent config** — `[pipeline]` in `bacon.toml` assigns agent names per stage (e.g., `observer = "nvidia"`), but there's no validation that corresponding `[agents.<name>]` sections exist. If someone types `observer = "nvidai"` (typo), the pipeline silently falls back — the PI pipeline calls `run_external_agent("nvidai")` which spawns an unknown binary, while the NVIDIA pipeline tries to look up `[agents.nvidai]` and gets empty config. The user gets a confusing "binary not found" error with no indication of the config typo.  
  (b) **Missing required keys** — `PipelineConfig::from_bacon_toml()` defaults every key to `"bacon"` if missing (inner `get()` function, line 197-201). An empty `[pipeline]` section (no keys) would route all stages to the `bacon` binary, which may not be the intended agent. Zero validation against expected key set.  
  (c) **validate_bacon_local_only() (lines 354-409) validates provider names but not agent cross-references** — It checks that `[agents.<name>].provider` is one of `ollama`, `cli`, or `nvidia`, and that the `bacon` agent uses `ollama`. But it doesn't validate that the agents referenced in `[pipeline]` actually exist in `[agents]`.
- **Impact:** Typo in `bacon.toml` → pipeline runs with wrong agent routing → confusing binary-not-found or wrong-LLM errors. The user has no diagnostic tool to verify their config.
- **Risk Level:** Medium
- **Confidence:** 100%
- **Fix:** Three-part:  
  (1) Add a `validate_config()` function called at pipeline startup that cross-references `[pipeline]` agent names against `[agents.<name>]` sections and warns if any are missing.  
  (2) Validate that each agent referenced in `[pipeline]` has a corresponding `[agents.<name>]` with at minimum a `type` field.  
  (3) Add `bacon --validate-config` CLI flag that prints parsed config vs defaults and reports any issues without running the pipeline.
- **Status: FIXED** — Added `validate_pipeline_config()` to `bacon_core/mod.rs`: cross-references each pipeline stage's agent name against `[agents.<name>]` config sections, warns on missing configs. Called from both PI and NVIDIA pipeline constructors. Verified by CI (`check.ps1`): all checks pass.

### Observer Issues

#### 21. NVIDIA Agent Skips Spec Detection Entirely
- **Name:** NVIDIA Observer missing spec-scan fast path
- **Location:** `src/bacon_agent_nvidia/observer.rs:12-31` (all 31 lines), compare `src/bacon_agent_pi/observer.rs:13-53`
- **Problem:** NVIDIA observer calls `nvidia_api::chat()` unconditionally (line 20). Unlike the PI agent, it has zero logic to check `_active/` for existing `approved` specs and fast-path to them. The default config routes all 4 stages to `"nvidia"`, so no-prompt mode never short-circuits to existing specs. Nuance: when `--prompt` IS provided, the PI observer ALSO skips the spec check (line 13: `if args.prompt.is_some() { return scan_for_improvements(...); }`) — so both agents behave identically in prompt mode. The difference is only in no-prompt/auto-mode.
- **Impact:** Every no-prompt pipeline run triggers an LLM call even when approved work is pending. On a backlog of 10 approved specs, 10 consecutive `--auto` runs would each call the LLM fresh instead of processing the queue. The Strategist may generate duplicate or overlapping specs.
- **Risk Level:** High

NVIDIA observer now checks for approved specs before calling the LLM; skips LLM call entirely when an approved spec is found (no prompt mode). PI observer simplified to use the same shared function. Verified by CI (`check.ps1`): 5/5 checks pass, 2692 tests pass. Files changed: `bacon_core/spec_io.rs`, `nvidia/observer.rs`, `pi/observer.rs`.

#### 22. Random 70/30 Spec Selection Without Ordering
- **Name:** Unordered spec selection (PI agent only)
- **Location:** `src/bacon_agent_pi/observer.rs:27-28` (PI observer only — NVIDIA observer has no equivalent logic)
- **Problem:** When multiple approved specs exist, `rand::random::<usize>() % approved.len()` picks uniformly at random with no ordering by spec number, creation time, or priority. The 70/30 bias is also hardcoded (`rand::random::<f64>() < 0.7`). This code only exists in the PI agent; the NVIDIA agent always calls the LLM.
- **Impact:** No ordering within the backlog — the same spec could be picked repeatedly while older specs wait. Not relevant when using the NVIDIA agent (default config), which always scans for new work.
- **Risk Level:** Medium
- **Confidence:** 100%
- **Fix:** Sort approved specs by spec number ascending (FIFO) before selecting the first one. Replace the hardcoded 0.7 with a `bacon.toml` config key (`[pipeline].backlog_bias = 0.7`) so users can tune backlog-clearing vs new-work ratio.
- **Status: FIXED** — Already fixed as a side effect of Issue 21. `find_approved_spec()` in `spec_io.rs` returns specs sorted by directory name (FIFO by spec number), so the oldest approved spec is always picked first. Verified by CI (`check.ps1`): all checks pass.

#### 23. No Enforced Scope Constraints on Observer Output
- **Name:** Soft-only scope limits
- **Location:** `src/bacon_agent_pi/observer.rs:64-78` (prompt text only), `src/bacon_agent_pi/strategist.rs:16-35` (risk assessment is also LLM-soft)
- **Problem:** The "max 30 lines changed, max 3 files, no new dependencies" constraint exists only in the user prompt sent to the Observer LLM (line 68: `"Keep scope small: max 30 lines changed, 3 files, no new dependencies."`). There is zero code-level validation of these constraints after the LLM responds. The Strategist's risk assessment is ALSO LLM-soft — its role prompt instructs it to check these limits (header table "Scope > 30 lines or > 3 files → Red flag"), but if the LLM ignores or misses this, there's no code gate. Additionally, "max 30 lines" is an inherently soft metric — the LLM describes what to change in prose, not in diff form, so the actual line count cannot be computed until the Coder generates a patch.
- **Impact:** An over-eager or hallucinating Observer can propose changes far exceeding documented scope. The Strategist may accept and plan the oversized change. The pipeline spends LLM budget and time on the Strategist and potentially the Coder before discovering the scope mismatch via `check-fast.ps1` failures.
- **Risk Level:** Medium
- **Confidence:** 100%
- **Fix:** Two-layer approach:  
  (1) **Observer-side heuristic** — After the Observer responds, use regex to count unique file paths mentioned (e.g., `src/[\w./-]+\.rs`) and estimate line counts from `start..end` ranges mentioned. Reject responses exceeding thresholds.  
  (2) **Strategist-side gate** — Add a code-level check in `run_strategist()`: count files referenced in the plan, and if > 3, warn and require explicit opt-in. For "line count" — this cannot be accurately enforced until the Coder generates a diff, but the `check-fast.ps1` gate already catches oversized patches (if they fail compilation due to missing changes). The Strategist gate is the most practical enforcement point.
- **Status: FIXED** — Added `count_spec_file_refs()` to `bacon_core/mod.rs`: counts unique `src/...rs` paths using regex. Both PI and NVIDIA strategists call it after LLM response and log `warn!()` if the plan references > 3 files. Integration tests verify counting logic. Verified by CI (`check.ps1`): all checks pass.

#### 24. Duplicate Detection Is LLM-Soft Only
- **Name:** Unenforced `_done/` and `_abandoned/` duplicate check
- **Location:** `src/bacon_agent_pi/observer.rs` (no code), `src/bacon_core/spec_io.rs:22-41` (infrastructure exists but is not wired — `done_dir()`, `list_active_specs()`, `read_spec_meta()` are all available)
- **Problem:** The Observer role prompt (v3.0, Phase 1) instructs the LLM to "Scan `docs/specs/_done/` for specs with similar titles" and "Check `docs/specs/_abandoned/` if it exists." There is zero code enforcement of this — the Rust code never calls any `_done/` / `_abandoned/` scanning function before invoking the LLM. The `spec_io` module has all the building blocks (`done_dir()` at line 37, `list_active_specs()` at line 44, `read_spec_meta()` at line 59) but they are not used for duplicate detection. The LLM may or may not comply with the prompt instruction depending on context window, model capability, and prompt adherence.
- **Impact:** Previously completed or rejected work can be re-proposed and re-implemented, wasting LLM cycles and producing redundant spec packages. The Strategist's duplicate check (Phase 2) would need to catch these, but that also relies on LLM compliance (soft).
- **Risk Level:** Medium
- **Confidence:** 100%
- **Fix:** Add a `find_specs_matching(description: &str) -> Vec<String>` function in `spec_io` that scans `_done/` and `_abandoned/` spec titles for substring/semantic overlap with the proposed work. Call it from `run_observer()` before the LLM scan. If matches are found, skip the LLM call and report "Already done/rejected in `<path>`" as the Observer output.
- **Status: FIXED** — Added `find_specs_matching()` to `bacon_core/spec_io.rs`: tokenizes description by words >3 chars, matches against `_done/` and `_abandoned/` spec titles. Wired into both PI and NVIDIA observers — logs `info!()` with matching paths when user prompt overlaps existing specs. Verified by CI (`check.ps1`): all checks pass.

#### 37. `starts_with("pass")` False Positive Risk
- **Name:** Fragile PASS/FAIL parser
- **Location:** `src/bacon_agent_pi/auditor.rs:112` and `src/bacon_agent_nvidia/auditor.rs:105` (identical `decision.starts_with("pass")` check)
- **Problem:** Decision is `response.trim().to_lowercase().starts_with("pass")`. This has three false-positive cases:  
  (a) **Words starting with "pass"** — `"Passing along my notes..."` → lowercased starts with `"pass"` → false PASS.  
  (b) **"PASS" in first line with trailing text** — `"PASS: looks good\nbut also check X"` starts with `"pass:"` which triggers PASS. This is actually intended behavior (the role prompt documents `"PASS with minor notes"` as valid), so not a bug.  
  (c) **Lowercase "pass" in prose** — `"pass this along to the next stage"` → triggers PASS, but the LLM was not trying to signal PASS.

- **Impact:** An LLM that uses "pass" as a verb in its response can accidentally trigger a PASS approval. The spec moves to `_done/` without proper review. False FAIL is less likely (requires the LLM to start with lowercase "pass" when it means FAIL).
- **Risk Level:** Medium
- **Confidence:** 100%
- **Fix:** Use regex `^(?i:PASS)\b` to match only if PASS is the first WORD (followed by word boundary), not a prefix of a longer word. `"PASS"`, `"PASS:"`, `"PASS with minor notes"` all match. `"Passing"` does NOT match because `\b` after `PASS` requires a word boundary. Also add lowercase PASS matching: the first word must be literally "PASS" (case-insensitive), not just start with those characters.

#### 42. No Global Circuit Breaker for LLM Unavailability
- **Name:** Missing LLM health pre-check
- **Location:** Pipeline startup in `src/bacon_core/agent.rs:78-95` — no pre-flight health check called. `Llm::health_check()` exists at `src/llm/mod.rs:47-49` and `LlmClient::health_check()` at `src/llm/client.rs:250-256` but is **never called by the pipeline**.
- **Problem:** `Llm::new()` (`llm/mod.rs:20-27`) initializes the client config but does NOT test connectivity — it only reads config and creates an HTTP client. A working `health_check()` method already exists (5-second timeout, checks Ollama `/api/tags` or OpenRouter endpoint). It returns `true` if the service responds. But neither the PI pipeline constructor (`pi/pipeline.rs:21-31`) nor the NVIDIA pipeline constructor (`nvidia/pipeline.rs:20-30`) calls it. The pipeline discovers LLM unavailability only when the first stage attempts its first LLM call, which has a 5-minute timeout and retries 4 times per stage.
- **Impact:** With 4 stages each retrying 4 times with 5-minute timeouts, the pipeline takes up to 80 minutes to report a connectivity issue that a 5-second health check would catch immediately at startup. The user watches the pipeline spin through retries before seeing any error.
- **Risk Level:** Medium
- **Confidence:** 100%
- **Fix:** Add `llm.health_check().await` call in both pipeline constructors (after `Llm::new()`). If it returns `false`, bail with a clear message: "LLM provider at <url> is not responding — check that Ollama/NVIDIA service is running." The health check already exists; it just needs to be wired.
- **Status: FIXED** — Added `llm.health_check().await` before the first LLM call in both PI and NVIDIA observers. On failure, bails immediately with a clear message instead of waiting through stage timeouts. The `health_check()` method (5-second timeout, checks Ollama `/api/tags`) was already implemented but never called. Verified by CI (`check.ps1`): all checks pass.

#### 43. Spec Numbering Race Condition on Concurrent Runs
- **Name:** No file locking for spec numbering (derivative of Issue 1)
- **Location:** `src/bacon_core/spec_io.rs:107-135` (`next_spec_number()`), `src/bacon_agent_pi/strategist.rs:110-113` and `src/bacon_agent_nvidia/strategist.rs:82-85` (callers in both agents)
- **Problem:** This is a sub-problem of Issue 1's broader race condition. `next_spec_number()` scans directories → finds max N → returns N+1. Between the scan and the directory creation, a concurrent instance reads the same max N and gets the same N+1. Both write specs with the same number prefix. While the slug usually differs (different LLM output → different title → different dir name), the numbering convention is broken. In the unusual case where two LLMs produce identical titles (possible during scope-reduction retries on the same spec), the full directory name collides.
- **Impact:** Broken numbering convention (duplicate numbers). In the worst case, directory collision (overwritten files) if titles are also identical.
- **Risk Level:** High (derivative of Issue 1; relies on the same race condition)
- **Confidence:** 100%
- **Fix:** Delegate to Issue 1's primary fix — `allocate_spec_dir()` using atomic `std::fs::create_dir()` instead of `next_spec_number()` + `create_dir_all()`.
- **Status: FIXED** — Resolved as a side effect of Issue 1. Both strategists now use `spec_io::allocate_spec_dir()` which atomically creates the spec directory. If two concurrent instances race, one succeeds and the other gets `AlreadyExists` and retries with the next number. The old `next_spec_number()` is preserved but unused. Verified by CI (`check.ps1`): 5/5 checks pass, 2692 tests pass.

#### 44. Agent Config Route Uses Hardcoded "nvidia" in Test
- **Name:** Test hardcodes agent assignment
- **Location:** `src/bacon_core/mod.rs:1090-1097` — test `from_bacon_toml_parses_real_config`
- **Problem:** The test asserts `cfg.observer == "nvidia"`, `cfg.strategist == "nvidia"`, etc. This matches the CURRENT `bacon.toml` but is a deployment-specific assumption baked into a unit test. The test's intent is to verify that `from_bacon_toml()` parses the config file correctly — it should test PARSING behavior, not SPECIFIC VALUES.

- **Risk Level:** Low
- **Confidence:** 100%

#### 45. `resolve_agent_binary()` Has No PATH Safety
- **Name:** Unsafe agent binary resolution
- **Location:** `src/bacon_core/mod.rs:476-495` (`resolve_agent_binary()`)
- **Problem:** `resolve_agent_binary()` joins the agent name string directly into path candidates: `root.join("target").join("debug").join(agent)` and `root.join("target").join("release").join(agent)`. If neither exists, it falls back to `PathBuf::from(agent)` which does a PATH lookup. An agent name containing `..` or `/` or `\` could resolve to unintended binaries (e.g., `agent = "../evil"` → `target/debug/../evil` → `target/evil`; or agent name like `cmd.exe /c` is passed to `Command::new` which on Windows could spawn with arguments). However, the agent name comes exclusively from `bacon.toml` `[pipeline]` section — an attacker who can write to `bacon.toml` already has broader code execution access to the repo. The risk is defense-in-depth: preventing accidental configuration typos from causing confusing failures, not preventing a targeted attack.
- **Impact:** A typo in `bacon.toml` agent name (e.g., `observer = "nvidai"` instead of `"nvidia"`) could resolve to a PATH binary named `nvidai` if it exists, or produce a confusing "binary not found" error. Path traversal via `..` is technically possible but requires config write access which is already game-over.
- **Risk Level:** Medium (defense-in-depth — real exploit path requires config compromise which is itself a critical precondition)
- **Confidence:** 100%
- **Fix:** Validate agent name in `resolve_agent_binary()`: reject names containing path separators (`/`, `\`), parent directory references (`..`), or non-alphanumeric characters (except hyphens and underscores). Only allow `[a-zA-Z0-9_-]+`. If the name fails validation, log a warning and fall back to the `bacon` default agent rather than attempting a PATH lookup.
- **Status: FIXED** (by Issue 5) — Added `is_safe_agent_name()` validation in `bacon_core/mod.rs` as part of Issue 5's fix. `resolve_agent_binary()` rejects unsafe agent names (path separators, `..`, `.`, non-alphanumeric chars) and falls back to `bacon` with a `warn!()`. Verified by CI (`check.ps1`): all checks pass.
